# 问题三正式求解说明

## 唯一正式方案

`plan_windows_opt.json` 是问题三以及问题四的唯一正式输入。当前指标：

- 运输架次 22，中继架次 4，货箱 80；
- 联合完成时间 8915.079576916525 s；
- 总能耗 75.97813472150902 kWh；
- 硬时限违反、加权延误、通信缺口均为 0；
- 0.1 s 自适应连续认证：未认证时长 0。

`plan_3relay_*.json`、`exp*.json` 均为实验候选，不得传给问题四。三中继候选仍有
43.595 s 连续通信区间未获认证。

## 修复内容

原窗口优化器把服务结束时刻二分到可行边界，只用旧通信判据验收，导致正式四中继方案仍有
1.227 s 亚秒级边界未获更紧连续证书认证。`q3_relay_window_opt.py` 现默认给每条中继窗口保留
1.0 s 安全裕量，并按实体机复用关系重算后续出发、返航、充电和能耗。

`q3_validate.py` 是正式验收入口，覆盖货箱唯一性、载荷与 SOC、时限、四类资源区间、
中继物理量、通信表连续性、PixelIsPoint 地形口径、0.1 s 自适应连续认证及汇总指标重算。

```powershell
python q3_validate.py
python q3_cont_cert.py --plan plan_windows_opt.json --resolution 0.1
```

两条命令都应返回 0；正式校验输出应包含 `未认证 0.000000 s` 和 `PASS`。

## 模型口径依据

- 自由空间路径损耗采用 ITU-R P.525：<https://www.itu.int/rec/R-REC-P.525-5-202411-I/en>。
- DEM 的 `GTRasterTypeGeoKey=PixelIsPoint` 按 GDAL RFC 33 处理半像元偏移：
  <https://gdal.org/en/stable/development/rfc/rfc33_gtiff_pixelispoint.html>。
- 无人机通信中的三维部署与通信—轨迹联合建模可参见 Mozaffari 等的综述：
  <https://arxiv.org/abs/1803.00680>。
- 以视距约束确定中继位置的建模背景可参见 Burdakov 等：
  <https://journals.sagepub.com/doi/10.1177/0278364910369463>。

这些资料用于确认传播、栅格和中继建模口径；具体坐标、库存、时限及能耗参数仍完全取自题目数据。

## 候选组合晋级规则

`q3_portfolio_audit.py` 将公开仓库中的“多候选方案+联合复核”思路落地为一道强制门槛：

1. 先检查通信缺口、硬时限违反和加权延误均为 0；
2. 再通过 0.1 s 自适应连续通信认证；
3. 只有通过前两步的方案，才能比较完成时间、能耗与架次。

审计表明，问题二的 5792.101 s 方案直接套用当前中继时，仍有
2806.414 s 通信缺口，涉及 8 个运输架次，因此被正确拒绝晋升。
这也说明“Q2 最快”不等于“Q3 最优”。
